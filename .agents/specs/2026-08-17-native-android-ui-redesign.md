# Native Android-inspired frontend redesign

## Request

Redesign Basketra's frontend so every primary view and shared visual primitive feels like one professional native Android application: compact, task-oriented, fluid, accessible, visually homogeneous, mobile-first, and easy to understand.

This is a design-only change. Preserve business behavior, backend/API/database contracts, routes, security boundaries, private-network assumptions, and OCR/AI semantics. The user explicitly permits rebuilding frontend view structure where useful and has granted standing approval for reversible design-only work on this pull request. Progress must be demonstrated with real browser screenshots.

## Evidence

- Basketra is a dependency-free HTML/CSS/JavaScript PWA served by the existing Node.js process.
- `package.json` pins Node.js 22.23.1 and pnpm 10.15.0 and exposes `pnpm quality` plus Playwright browser testing.
- `src/web/index.html` owns Home, Lists, Tickets, Plans, Settings, dialogs, and primary navigation.
- `src/web/styles.css` owns the structural/base UI rules; `src/web/modern.css` is the current visual override layer; `src/web/operations.css` adds Settings-specific presentation.
- Existing SVG icons and shared interaction behavior live in `ui.js`; feature markup is generated by `lists.js`, `receipts.js`, and `operations.js`.
- There is no Storybook, component framework, external icon library, or runtime design-system dependency.
- Existing Playwright coverage already captures mobile and desktop evidence and the repository publishes PR visual evidence.
- Baseline screenshots show inconsistent density, containment, and desktop use across Home, Lists, Tickets, and Settings.
- The canonical UI/UX guide requires mobile-first design, WCAG 2.2 AA, enabled zoom, visible focus, 44px-class touch targets where reasonable, reduced motion, semantic native controls, reusable tokens, and restrained card usage.
- Material Design 3 is a reference for Android-native hierarchy and adaptive scaffolding only; it is not a dependency.

## Decision

1. Treat Basketra as one adaptive Android-inspired product rather than independently styled pages.
2. Keep the dependency-free runtime and existing SVG icon system.
3. Preserve the green product identity through semantic light/dark tokens for surfaces, text, primary, outline, success, warning, error, focus, spacing, shape, and motion.
4. Keep five destinations. Compact screens use a bottom navigation bar; expanded screens use a persistent navigation rail with the same order and semantics.
5. Replace general card stacking with proximity, dividers, tonal containers, and rows. Keep containment only for real entities or grouped tasks.
6. Use one shared language for filled, tonal, outlined, text, danger, and icon actions; fields; switches; status chips; progress; dialogs; sheets; and feedback.
7. Use native `<dialog>` semantics. Compact presentation behaves like a bottom sheet; wider layouts center the same dialog.
8. Preserve zoom, 320 CSS px reflow, keyboard operation, accessible names, current IDs, and gesture alternatives.
9. Respect `prefers-reduced-motion`; motion is short and communicates navigation/state only.
10. Keep CSS ownership explicit: `styles.css` structural/base, `modern.css` canonical visual system, `operations.css` operations-specific layout that consumes shared tokens.

## Flow

### Home

Task-first launch screen. Primary action is Lists; Ticket capture and Plans are secondary. Private-network status is supporting information, not decorative hero content.

### Lists

Overview uses compact list entities with one clear create action. Detail uses back/title/realtime/overflow, then add-product, pending items, completed items, and optional AI. Existing swipe and button alternatives remain unchanged.

### Tickets

One continuous workflow: capture pages, queue/progress, extraction/verification, review, confirmation. Capture rows show thumbnail, stage, progress, and contextual actions without nested cards.

### Plans

One concise explanation and run action. Result entities prioritize strategy and cost with restrained metadata.

### Settings

Runtime, AI diagnostics, Logs, and Backup/Restore are separate settings groups. Mobile is one vertical stack; expanded layouts use a two-column supporting layout. Destructive restore remains visually isolated.

## Mobile design

- One-column flow with 16px-class gutter and safe-area handling.
- Compact top app bar and persistent five-destination bottom navigation.
- Primary controls generally use 44-48 CSS px touch targets.
- No oversized marketing typography.
- Inputs remain usable with the virtual keyboard and at 200% zoom.
- Fixed navigation must not cover focused fields, errors, or actions.

## Desktop adaptation

- Persistent navigation rail on expanded layouts.
- Bounded readable content instead of a narrow centered phone column.
- Lists and Tickets preserve the same task sequence.
- Settings may use two columns because its operational groups are independent.
- No desktop-only business behavior.

## Visual system

Canonical semantic tokens cover:

- background, surface, low/high surface containers;
- on-surface text and variants;
- outline and outline-variant;
- primary, primary-container, on-colors;
- success, warning, error containers and on-colors;
- focus ring;
- spacing rhythm;
- small/medium/large/full shape roles;
- motion duration/easing;
- app-bar/navigation dimensions and content widths.

Shared visual primitives: app bar, navigation bar/rail, buttons, icon buttons, rows, chips, fields, switches, section headers, dialogs/sheets, toast, progress, empty/error states, capture rows, and comparison cards.

## Accessibility

- Native semantic controls before ARIA.
- Skip link, landmarks, heading order, labels, and dialog semantics remain intact.
- Full keyboard access and visible `:focus-visible` treatment.
- Important state never depends on color alone.
- WCAG 2.2 AA contrast target.
- Primary mobile controls generally >=44x44 CSS px.
- 320 CSS px and 200% zoom are explicit acceptance cases.
- Reduced motion disables nonessential transitions/transforms.

## Risks and rollback

Global visual changes can hide controls, create reflow issues, or expose specificity conflicts. Work is split into atomic reversible commits and validated by real browser evidence. The adaptive rail must remain the same navigation architecture rather than a separate desktop product.

Rollback is commit-by-commit: specification, shared system, Settings integration, and visual tests can each be reverted independently.
